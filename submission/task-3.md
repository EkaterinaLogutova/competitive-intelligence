# Задание 3 Автоматизация и использование данных

Я бы разделила работу на исследовательский и эксплуатационный циклы. В исследовательском
цикле мы собираем выборку, уточняем классы, проверяем гипотезы и сравниваем методы. В
эксплуатационном — регулярно обновляем уже изученные источники и контролируем отклонения.
Без первого цикла автоматизация быстро превращается в набор исключений для сайтов; без
второго модель остается отдельным опытом, который нельзя использовать в рабочей системе.

## 3 1 Автоматизация сбора

### Реестр и единица работы

Для каждого URL нужен паспорт: домен, тип страницы, частота, допустимый способ доступа,
версия модуля и состояние последнего запуска. Заданием для сборщика является не
«обойти сайт», а получить конкретную страницу или изменение за заданное временное окно.

Сначала выбирается наиболее устойчивый способ получения:

1. официальный программный интерфейс или выгрузка;
2. новостная лента или карта сайта;
3. обычный запрос к странице;
4. браузер, если данные появляются только после выполнения сценариев страницы.

Блокировка или проверка на робота регистрируется как результат, а не как приглашение
усиливать обход. До регулярного сбора проверяются правила площадки, файл robots.txt,
условия хранения и наличие персональных данных.

### Сохранение наблюдений

Сырой ответ сохраняется до извлечения. Вместе с ним записываются время, конечный URL,
HTTP-статус, размер, хеш и версия сборщика. Это дает две возможности: воспроизвести
ошибку и повторно обработать страницу после изменения схемы, не обращаясь к сайту.

Нормализованная запись содержит общий конверт и типизированную часть. Например, у отзыва
есть оценка и объект, у темы форума — число ответов и последний участник, у новостной
карточки — издание, ссылка на сюжет и исходную статью.

### Сбор только новых и изменившихся материалов

Полный архив не нужно скачивать при каждом запуске. Сначала проверяется индекс. Новые и
изменившиеся материалы определяются по ID, URL, времени и хешу. Пагинация прекращается,
когда достигнут уже известный диапазон. Повторные запросы выполняются только для
временных ошибок и с ограничением по домену.

В небольшой версии это один процесс по расписанию. При росте появляются очередь и
раздельные процессы для обычных и браузерных запросов, но состав записи не меняется.

### Хранение

Я бы использовала:

- объектное хранилище для HTML и других исходных материалов;
- PostgreSQL для реестра, запусков, разметки и связей между документами;
- поисковый индекс для текста и фильтрации;
- колоночное хранилище только тогда, когда объем временных метрик оправдает отдельный
  слой.

В реляционной базе удобно хранить связи и версии разметки. Тексты и редко используемые
признаки можно временно хранить в полуструктурированном виде, пока их схема уточняется.

## 3 2 Классификация источников и извлечение полей

### Подготовка корпуса

Шесть URL подходят для проектирования схемы классов, но не для обучения модели.
Следующий шаг — собрать страницы нескольких типов и доменов. Train/test split нужно
делать по доменам. Случайное разбиение страниц одного сайта завысит результат, потому
что модель просто узнает его верстку.

Разметка ведется на трех уровнях:

```text
тип площадки → тип страницы → тип материала
```

Для неоднозначных примеров сохраняются обе оценки разметчиков и причина расхождения.
Качество инструкции определяется не только числом готовых строк. Нужно проверить,
насколько часто два разметчика независимо дают одинаковый ответ. Для этого подойдет
коэффициент согласованности Кохана.

### Признаки

Для первой версии я бы собрала три группы признаков:

- адрес и метаданные: путь, параметры адреса, заголовок, описание и тип страницы;
- структура: число повторяющихся блоков, таблиц, форм, страниц пагинации, счетчиков и
  ссылок на другие домены;
- текст: заголовок страницы, навигация, короткие фрагменты карточек и их числовые
  представления по смыслу.

Структурные признаки дешевле полного текста и часто хорошо объясняют решение. Текстовые
нужны там, где одинаковый шаблон используется для разных типов материалов.

### Последовательность экспериментов

Сначала нужна простая точка отсчета. Я бы сравнила:

1. правила по известным признакам;
2. логистическую регрессию на разреженных и числовых признаках;
3. градиентный бустинг на структурных признаках;
4. небольшую модель для анализа текста или его смысловых представлений;
5. совместную схему: правила для надежных случаев, модель для остальных.

Для каждого варианта измеряются macro-F1, confusion matrix, время на страницу и
стоимость обработки тысячи страниц. Более сложная модель оправдана,
только если улучшение качества перекрывает рост задержки и сложности поддержки.

Извлечение полей проверяется отдельно от определения типа страницы. Для дат, ссылок и
чисел используется exact match. Для текста — полнота, лишние фрагменты и символьное
сходство. Для списков считаются precision, recall и F1.

### Новые типы страниц

Модель не должна обязательно выбирать один из известных классов. Страница получает
метку «неизвестный тип», если уверенность мала, два наиболее вероятных класса близки,
структура страницы изменилась или выросла доля пустых полей.

Проверить этот механизм можно с помощью leave-one-class-out: по очереди исключать один
тип страниц из обучения и смотреть, распознается ли он как неизвестный. Основные
показатели — recall неизвестного класса и доля знакомых страниц, ошибочно отнесенных к
неизвестным.

Новые примеры группируются по структурным и текстовым признакам. Аналитик размечает
небольшую разнообразную выборку из группы. После этого либо расширяется существующий
класс, либо создается новый. Так активное обучение направляет ручную работу в места, где
она дает максимальную информацию.

## 3 3 Что можно построить для медиамониторинга

### Автоматическая разметка документов

Базовые задачи — тема, тип материала, организации и персоны, география, язык, тональность
и аспект оценки. Для отзывов общей оценки тональности недостаточно: жалоба на поддержку и
положительная оценка продукта могут находиться в одном тексте. Поэтому тональность
лучше связывать с аспектом и конкретным фрагментом.

Разметка хранит версию модели и уверенность. Низкая уверенность направляет документ на
ручную проверку, а исправление возвращается в обучающий корпус.

### Группировка дублей и сюжетов

Точный дубль определяется по URL и хешу нормализованного текста. Публикации об одном
событии объединяются отдельно: по времени, сущностям, похожести заголовка и текста.
Нельзя удалять все похожие материалы как дубли — независимые источники нужны для оценки
распространения и подтверждения сюжета.

### Исследуемые информационные метрики

Я бы начала с нескольких интерпретируемых признаков и проверила их связь с экспертной
оценкой значимости:

| Метрика | Рабочее определение | Для чего может быть полезна |
|---|---|---|
| Новизна | единица минус максимальное сходство с недавними материалами | отделять новый факт от повторения |
| Разнообразие источников | нормированная энтропия изданий в сюжете | отличать широкое распространение от перепечаток одной сети |
| Скорость распространения | новые независимые публикации за единицу времени | раннее обнаружение растущего сюжета |
| Информационная плотность | число уникальных сущностей и проверяемых утверждений на объем текста | снижать вес длинных малосодержательных материалов |
| Подтвержденность | число независимых источников для утверждения | оценивать устойчивость вывода |
| Вовлеченность | нормализованные реакции относительно базового уровня площадки | находить аномальный интерес |

Это пока гипотезы, а не готовые показатели работы. Для каждой метрики нужен набор сюжетов с экспертной
разметкой и проверка устойчивости по тематикам, языкам и типам площадок.

### Генерация производной информации

Практический сценарий — краткий дайджест по сюжету. Я бы сравнила три метода:

1. выбрать наиболее репрезентативные предложения без генерации;
2. построить шаблонную сводку из сущностей, времени и метрик;
3. сгенерировать текст моделью по найденным документам.

В третьем варианте поиск сначала ограничивает корпус периодом, темой и правами доступа,
затем выбирает подходящие материалы по словам и смыслу. Модель получает только найденные
фрагменты и ссылки на них. Такой подход часто называют RAG. Здесь он решает одну
конкретную задачу: помогает составить сводку по уже собранным данным, но не заменяет
сбор и классификацию страниц.

В ответе должны сохраняться ссылки на исходные документы. Если источники расходятся,
это отражается в сводке; если контекста недостаточно, система не дополняет его знаниями
модели.

Оценка такого эксперимента включает:

- покрытие фактов из эталонной сводки;
- долю утверждений, подтвержденных переданными документами;
- точность ссылок;
- число пропущенных существенных расхождений;
- время аналитика на проверку и исправление;
- задержку и стоимость генерации.

Сначала я бы проверила, дает ли генерация выигрыш по сравнению с простым выбором
предложений из исходных текстов.
Если аналитик тратит на исправление больше времени, чем на самостоятельную сводку,
улучшение стилистики не имеет продуктовой ценности.

### Ранжирование и оповещения

Специализированные метрики можно использовать как признаки модели значимости. На входе
— новизна, скорость, число независимых источников, вовлеченность и приоритет сущности; на
выходе — вероятность того, что сюжет потребует внимания аналитика.

Обучающей меткой может быть действие пользователя: открытие сюжета, добавление в отчет,
эскалация или ручная оценка. При этом нужно учитывать смещение обратной связи: аналитик
видит прежде всего то, что уже подняла текущая система.

### Масштабирование на другие языки

Я бы сравнила два подхода: перевод в один язык и многоязычную модель. Первый проще
контролировать, но ошибки перевода влияют на сущности и тональность. Второй сохраняет
исходный текст, однако требует отдельных тестовых наборов по языкам.

Нельзя считать хорошее среднее качество доказательством одинаковой работы на всех
языках. Метрики рассчитываются отдельно по языку, тематике и типу источника; для редких
групп сохраняется возможность ручного маршрута.

## Ближайшие эксперименты

| Эксперимент | Данные | Сравнение | Результат |
|---|---|---|---|
| Тип страницы | размеченные страницы разных доменов | правила и простая модель | macro-F1 и время |
| Неизвестный класс | leave-one-class-out | пороги уверенности | recall неизвестного класса |
| Группировка сюжетов | пары и группы новостей | частотные признаки и смысловые векторы | качество объединения пар |
| Значимость сюжета | экспертные оценки | отдельные показатели и общая модель | качество первых результатов списка |
| Дайджест | группы новостей с эталонными сводками | выбор предложений, шаблон и генерация по найденным текстам | подтвержденность и время проверки |

Такой порядок позволяет двигаться от данных и простого решения к моделям, каждый раз
понимая, какое улучшение получено и сколько оно стоит.
